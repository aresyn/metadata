# PRD: Генератор `Report.txt` по Git-выгрузке 1С для MCP

## 1. Название

**1C Configuration Report Generator**

Рабочее имя:

```text
 generate-config-report
```

## 2. Контекст

Используется MCP `CodeMetadataSearchServer` для поиска по коду и метаданным 1С.

Код конфигурации уже хранится в Git в виде выгрузки 1С в XML/BSL. Для работы `metadatasearch` MCP нужен файл `Report.txt`, аналогичный штатному отчету Конфигуратора **“Отчет по конфигурации”**.

Сейчас `Report.txt` можно получить вручную через Конфигуратор. Цель — заменить ручной шаг автоматической генерацией из Git.

Целевая схема:

```text
Git XML/BSL
  ↓
generate-config-report
  ↓
metadata/Report.txt
  ↓
MCP INDEX_METADATA=true
```

Эталонный загруженный отчет показывает, что штатный `Report.txt` — это иерархическое дерево метаданных: корневой блок `Конфигурации.СистемаЗаказовБК`, свойства `Имя`, `Синоним`, `Комментарий`, `ПринадлежностьОбъекта`, роли, поставщик, версия и другие свойства конфигурации.

## 3. Главная цель

Разработать генератор, который по XML-выгрузке основной конфигурации 1С из `src\cf` и, при наличии, одного расширения из `src\cfe` формирует `Report.txt`, структурно и стилистически близкий к штатному отчету Конфигуратора **“Отчет по конфигурации”**.

## 4. Главный принцип

`Report.txt` должен быть отчетом **по метаданным**, а не отчетом по файлам Git.

Генератор не должен добавлять искусственные технические сведения:

```text
Модуль менеджера
Модуль объекта
Модуль формы
ПутьКФайлу
ФайлBSL
code/main
code/extensions
src/cf
src/cfe
GitCommit внутри каждого объекта
ПоисковыеТеги
Источник: Основная конфигурация
Источник: Расширение
```

Правильное разделение:

```text
Report.txt → дерево метаданных, свойства объектов, вложенные элементы
CODE_PATH  → XML/BSL-файлы для codesearch
```

Поиск по коду остается задачей MCP через `CODE_PATH`. Генератор `Report.txt` не должен дублировать `codesearch`.

## 5. Структура Git-репозитория

Ожидаемая структура:

```text
src\
  cf\
    Configuration.xml
    CommonModules\
    Catalogs\
    Documents\
    InformationRegisters\
    AccumulationRegisters\
    AccountingRegisters\
    Reports\
    DataProcessors\
    Enumerations\

    Roles\
    ...

  cfe\
    Configuration.xml
    CommonModules\
    Catalogs\
    Documents\
    InformationRegisters\
    Reports\
    DataProcessors\
    ...
```

Где:

```text
src\cf  — обязательная основная конфигурация

```

Расширения может не быть. Отсутствие `src\cfe` не является ошибкой, если `extensionRequired=false`.

## 6. Среда выполнения

### 6.1. Текущая среда

Ожидаемая среда:

```text
Windows 10/11 или Windows Server
PowerShell
Git for Windows
Python 3.11+
локальный clone Git-репозитория
```

Примеры путей:

```text
E:\mcp-1c\repos\orders
E:\mcp-1c\staging\orders\current\metadata

```

### 6.2. Будущая среда

В перспективе генератор должен переехать на Linux без переписывания бизнес-логики.

Требования:

```text
- вся работа с путями через pathlib / path abstraction;
- не использовать Windows-only API;
- не использовать COM/OLE;
- не использовать реестр Windows;
- не использовать Конфигуратор 1С;
- не использовать UI automation;
- не зависеть от PowerShell внутри parser logic;
- принимать все пути из config-файла;
- корректно работать с \ и /;
- корректно работать с кириллицей;
- не зависеть от кодировки консоли Windows.
```

PowerShell допустим только как внешний runner на Windows.

## 10. Входные данные

### 10.1. Config-файл проекта

Пример:

```json
{
  "project": "orders",
  "repoPath": "E:/mcp-1c/repos/orders",
  "mainConfigPath": "src/cf",
  "extensionPath": "src/cfe",
  "extensionRequired": false,
  "outputPath": "E:/mcp-1c/staging/orders/current/metadata",
  "reportFileName": "Report.txt",
  "diagnosticsPath": "E:/mcp-1c/staging/orders/current/diagnostics",
  "logsPath": "E:/mcp-1c/staging/orders/current/logs",
  "encoding": "utf-8",
  "generatorSettingsPath": "E:/mcp-1c/projects/orders-generator-settings.json",
  "warningsAsErrors": false
}
```

### 10.2. Обязательные параметры

```text
project
repoPath
mainConfigPath
outputPath
reportFileName
```

### 10.3. Необязательные параметры

```text
extensionPath
extensionRequired
diagnosticsPath
logsPath
encoding
generatorSettingsPath
warningsAsErrors
```

Значения по умолчанию:

```text
extensionPath = "src/cfe"
extensionRequired = false
encoding = "utf-8"
generatorSettingsPath = встроенный generate_config_report/settings/defaults.json
warningsAsErrors = false
```

`generatorSettingsPath` — необязательный путь к JSON-файлу с правилами генерации.

В этот файл должны быть вынесены настраиваемые правила:

```text
- whitelist свойств по типам объектов;
- aliases XML-свойств к штатным русским именам свойств отчета;
- список типов метаданных и их папок в выгрузке;
- fallbackEnabled для неподдержанных типов;
- вложенные коллекции объектов;
- запрещенные технические свойства и фрагменты имен;
- формат отчета: базовый отступ, символ отступа, перевод строки, пустая строка между корневыми секциями;
- поддерживаемые кодировки.
```

Если `generatorSettingsPath` не задан, используется встроенный default-файл генератора.

Добавление нового alias, whitelist-свойства или типа метаданных не должно требовать изменения Python-кода, если не требуется новая логика разбора сложной XML-структуры.

Если `src\cfe` отсутствует и `extensionRequired=false`, генератор должен сформировать `Report.txt` только по основной конфигурации.

### 10.4. Правило `warningsAsErrors` и `--strict`

`warningsAsErrors` — опциональный параметр config-файла, задающий постоянную политику проекта.

`--strict` — CLI override для разового запуска, CI или ручной жесткой проверки.

Приоритет:

```text
--strict имеет приоритет над config-файлом.
Если передан --strict, поведение эквивалентно warningsAsErrors=true.
```

Правила:

```text
warningsAsErrors=false:
  warning не считается критической ошибкой;
  Report.txt формируется;
  exit code = 1, если warnings есть.

warningsAsErrors=true:
  warning трактуется как ошибка качества генерации;
  Report.txt может быть сформирован, но запуск считается неуспешным;
  exit code = 2.

--strict:
  принудительно включает warningsAsErrors=true независимо от значения в config.
```

## 12. Требования к формату `Report.txt`

### 12.1. Общий стиль

Файл должен быть похож на штатный отчет:

```text
	- Конфигурации.<ИмяКонфигурации>
		Имя: "<ИмяКонфигурации>"
		Синоним: "<Синоним>"
		Комментарий: ""
		ПринадлежностьОбъекта: "Собственный"
		ОбъектРасширяемойКонфигурации: ""
		...
		- Подсистемы.<ИмяПодсистемы>
			Имя: "<ИмяПодсистемы>"
			Синоним: "<Синоним>"
			Комментарий: ""
			Состав:
				"Документ.Заказ"
				"Справочник.Номенклатура"
```

### 12.2. Форматирование

```text
- иерархия задается табуляцией;
- формат должен соответствовать эталонному `ОтчетПоКонфигурации.txt`: весь отчет имеет базовый отступ в одну табуляцию;
- корневой объект начинается со строки "\t- <ПолноеИмяОбъекта>";
- объект на логическом уровне N выводится с отступом `N + 1` табуляций перед `- <ПолноеИмяОбъекта>`;
- свойства выводятся как <ИмяСвойства>: "<Значение>";
- списочные свойства выводятся отдельным блоком;
- вложенные объекты выводятся внутри родительского объекта;
- пустые строковые значения выводятся как "";
- булевы значения выводятся как "Истина" / "Ложь";
- порядок объектов должен быть стабильным;
- порядок свойств должен быть стабильным;
- между корневыми секциями основной конфигурации и расширения выводится ровно одна пустая строка;
- если расширения нет, лишняя пустая строка в конце Report.txt не добавляется;
- внутри корневых секций пустые строки между объектами не добавляются, если это не требуется для штатного представления многострочного свойства.
```

Пример корневых секций при наличии расширения:

```text
	- Конфигурации.<ИмяОсновнойКонфигурации>
		Имя: "<ИмяОсновнойКонфигурации>"
		...

	- Конфигурации.<ИмяРасширения>
		Имя: "<ИмяРасширения>"
		...
```

### 12.3. Кодировка

Default:

```text
UTF-8 без BOM
```

Параметр `encoding` должен поддерживать:

```text
utf-8
utf-8-sig
cp1251
```

Причина: текущая машина Windows, русские имена объектов и возможные особенности чтения файла MCP.

### 12.4. Правила порядка вывода

Корневые секции выводятся в фиксированном порядке:

```text
1. \t- Конфигурации.<ИмяОсновнойКонфигурации>
2. \t- Конфигурации.<ИмяРасширения>, если src\cfe есть
```

Объекты внутри корневой секции выводятся в порядке ссылок из `Configuration.xml` / `ChildObjects`, как в штатном отчете Конфигуратора.

Если объект поддержан генератором, но отсутствует в списке ссылок родительского XML, он выводится после объектов из эталонного порядка и сортируется по полному имени как fallback.

Вложенные элементы выводятся в порядке ссылок из XML родительского объекта:

```text
<Attribute>        → Реквизиты
<Form>             → Формы
<TabularSection>   → ТабличныеЧасти
<Command>          → Команды
<Template>         → Макеты
<EnumValue>/<Value> → Значения enum
```

Это важно для расхождений с алфавитной сортировкой. Например, в эталоне для `Документы.Заказ` сначала идут реквизиты в порядке XML, затем формы в порядке `<Form>`, затем табличные части, затем макеты.

Для элементов без ссылки в родительском XML используется fallback-сортировка по полному имени, чтобы отчет оставался детерминированным.

Свойства объекта не сортируются просто по алфавиту.

Правило:

```text
1. Поддержанные свойства из whitelist для конкретного типа объекта выводятся в фиксированном порядке, близком к штатному отчету Конфигуратора.
2. Дополнительные простые свойства, найденные в XML, выводятся после whitelist-свойств, отсортированные по имени свойства.
3. Сложные дополнительные XML-узлы не выводятся автоматически. Они фиксируются в diagnostics как unsupportedComplexProperty и могут быть добавлены в whitelist в следующих версиях.
```

Свойства, которые в штатном отчете всегда выводятся блоком списка даже при одном значении, задаются в `listPropertyNames` настроек генератора. Например: `Тип`, `СвязиПараметровВыбора`, `ПараметрыВыбора`.

## 13. Функциональные требования

### FR-001. Чтение основной конфигурации из `src\cf`

Генератор должен читать основную конфигурацию из:

```text
<repoPath>\<mainConfigPath>
```

Default:

```text
src\cf
```

Если каталог не найден, генерация завершается ошибкой.

### FR-002. Опциональное чтение расширения из `src\cfe`

Генератор должен поддерживать одно необязательное расширение из:

```text
<repoPath>\<extensionPath>
```

Default:

```text
src\cfe
```

Если каталог `src\cfe` существует, генератор должен:

```text
1. прочитать XML-выгрузку расширения;
2. определить имя расширения из Configuration.xml;
3. добавить расширение в тот же Report.txt;
4. вывести расширение отдельной корневой секцией;
5. не накладывать расширение на основную конфигурацию.
```

Если каталог `src\cfe` отсутствует:

```text
extensionRequired=false:
  - сформировать Report.txt только по src\cf;
  - записать warning в diagnostics;
  - завершиться с exit code 1;
  - если warningsAsErrors=true или передан --strict, завершиться с exit code 2.

extensionRequired=true:
  - не формировать успешный результат;
  - записать error в diagnostics;
  - завершиться с exit code 7.
```

## 14. Требования по расширению `src\cfe`

### FR-021. Расширение необязательно

В MVP поддерживается не более одного расширения:

```text
src\cfe
```

Расширение может отсутствовать.

Возможные режимы:

```text
1. Конфигурация без расширения:
   src\cf есть
   src\cfe отсутствует
   extensionRequired=false
   → Report.txt содержит только:
   	- Конфигурации.<ИмяОсновнойКонфигурации>

2. Конфигурация с расширением:
   src\cf есть
   src\cfe есть
   → Report.txt содержит:
   	- Конфигурации.<ИмяОсновнойКонфигурации>
   	- Конфигурации.<ИмяРасширения>

3. Расширение обязательно, но отсутствует:
   src\cf есть
   src\cfe отсутствует
   extensionRequired=true
   → ошибка exit code 7
```

### FR-022. Расширение выводится отдельной корневой секцией

Правильно:

```text
	- Конфигурации.<ИмяОсновнойКонфигурации>
		...

	- Конфигурации.<ИмяРасширения>
		...
```

Неправильно:

```text
	- Конфигурации.<ИмяОсновнойКонфигурации>
		...
		- Расширение.<ИмяРасширения>
```

### FR-023. Без merged-view

Генератор не должен объединять объекты основной конфигурации и расширения в итоговый объект.

Неправильно:

```text
Документ.Заказ = основной Документ.Заказ + изменения расширения
```

Правильно:

```text
Основная конфигурация:
	- Документы.Заказ

Расширение:
	- Документы.Заказ
		ПринадлежностьОбъекта: "Заимствованный"
		ОбъектРасширяемойКонфигурации: "<если есть в XML>"
```

## 15. Нефункциональные требования

### NFR-001. Максимальная близость к штатному отчету

Приоритеты:

```text
1. Не добавлять лишнего.
2. Сохранять штатные имена свойств.
3. Сохранять иерархию.
4. Сохранять стиль списков.
5. Сохранять кавычки значений.
6. Сохранять пустые значения как "".
7. Не выводить файловые пути.
```

### NFR-002. Детерминированность

Одна и та же Git-выгрузка должна давать одинаковый `Report.txt`.

Требования:

```text
- корневые секции выводятся в фиксированном порядке:
  1. основная конфигурация;
  2. расширение, если оно есть;

- объекты внутри корневой секции выводятся в порядке ссылок из `Configuration.xml` / `ChildObjects`, fallback — по полному имени;

- вложенные элементы выводятся в порядке ссылок из XML родительского объекта, fallback — по полному имени;

- свойства объекта выводятся не по алфавиту, а по заранее заданному списку свойств для типа объекта, близкому к штатному отчету Конфигуратора;

- неизвестные или дополнительные простые свойства выводятся после известных свойств, отсортированные по имени свойства;

- сложные дополнительные XML-узлы не выводятся автоматически;

- отсутствие timestamp внутри Report.txt;

- отсутствие commit SHA внутри Report.txt;

- отсутствие случайных GUID, если они не являются штатным свойством.
```

### NFR-003. Производительность

Генератор должен обрабатывать крупные конфигурации.

Ориентиры:

```text
- до 100 000 файлов;
- Report.txt размером до нескольких сотен МБ;
- потоковая запись результата;
- не держать весь отчет в памяти;
- время генерации должно быть существенно меньше времени индексации MCP.
```

### NFR-004. Кроссплатформенность

Несмотря на текущий запуск на Windows, код должен быть готов к Linux.

Требования:

```text
- Python pathlib для путей;
- отсутствие hardcoded backslash;
- отсутствие PowerShell внутри parser logic;
- отсутствие cmd.exe-зависимостей;
- отсутствие COM/OLE;
- отсутствие Windows registry;
- отсутствие зависимости от текущей кодировки консоли;
- все параметры через config/CLI.
```

### NFR-005. Windows-friendly behavior

На Windows генератор должен:

```text
- корректно работать с путями вида E:\mcp-1c\repos\orders;
- корректно работать с кириллицей в путях и файлах;
- писать лог в файл, а не только stdout;
- возвращать exit code для Task Scheduler;
- не требовать интерактивной сессии пользователя;
- не открывать GUI;
- не блокировать репозиторий для git pull после завершения.
```

### NFR-006. Linux-ready behavior

На Linux генератор должен:

```text
- запускаться тем же CLI;
- принимать пути вида /opt/mcp-1c/repos/orders;
- не требовать изменения формата config, кроме путей;
- писать stdout/stderr корректно для cron/systemd;
- использовать те же exit codes.
```

### NFR-007. Отказоустойчивость

Один поврежденный XML-файл не должен полностью останавливать генерацию, если можно продолжить.

Поведение:

```text
- ошибка фиксируется в report-diagnostics.json;
- проблемный объект пропускается или выводится частично;
- генерация продолжается;
- итоговый exit code зависит от критичности.
```

### NFR-008. Безопасность

Генератор не должен:


## 18. Exit codes

```text
0 — Report.txt успешно сформирован, warnings нет.
1 — Report.txt сформирован, есть warnings.
2 — Report.txt сформирован или частично сформирован, но warningsAsErrors=true или передан --strict.
3 — неверные параметры запуска.
4 — не найден путь основной конфигурации src/cf.
5 — не найдено ни одного объекта метаданных.
6 — ошибка записи Report.txt.
7 — extensionRequired=true, но src/cfe не найден.
8 — ошибка чтения config-файла.
```

Если `extensionRequired=false`, отсутствие `src\cfe` не является ошибкой.

## 20. Критерии приемки

### AC-001. Формируется `Report.txt`

После запуска создается:

```text
metadata\Report.txt
```

Файл не пустой и содержит:

```text
	- Конфигурации.<ИмяОсновнойКонфигурации>
```

### AC-002. Формат похож на штатный отчет

Объекты выводятся в формате:

```text
	- <ПолноеИмяОбъекта>
		Имя: "<Имя>"
		Синоним: "<Синоним>"
		Комментарий: "<Комментарий>"
```

### AC-003. Нет искусственных модульных полей

В `Report.txt` не должно быть искусственно добавленных строк:

```text
Модуль менеджера:
Модуль объекта:
Модуль формы:
ПутьКФайлу:
ФайлBSL:
code/main/
code/extensions/
src/cf
src/cfe
```

### AC-004. Подсистемы содержат состав

Для подсистем выводится:

```text
Состав:
	"Документ.Заказ"
	"Справочник.Номенклатура"
```

### AC-005. Общие модули содержат свойства исполнения

Для общих модулей выводятся:

```text
Глобальный
КлиентУправляемоеПриложение
Сервер
ВнешнееСоединение
КлиентОбычноеПриложение
ВызовСервера
Привилегированный
ПовторноеИспользованиеВозвращаемыхЗначений
```

### AC-006. Документы содержат реквизиты и табличные части

Для документа должны выводиться:

```text
- Документы.<Имя>.Реквизиты.<ИмяРеквизита>
- Документы.<Имя>.ТабличныеЧасти.<ИмяТЧ>
```

### AC-007. Регистры содержат измерения, ресурсы и реквизиты

Для регистра должны выводиться:

```text
- РегистрыСведений.<Имя>.Измерения.<Имя>
- РегистрыСведений.<Имя>.Ресурсы.<Имя>
- РегистрыСведений.<Имя>.Реквизиты.<Имя>
```

### AC-008. Отчеты и обработки содержат формы и макеты

Для отчетов и обработок должны выводиться:

```text
- Отчеты.<Имя>.Формы.<ИмяФормы>
- Отчеты.<Имя>.Макеты.<ИмяМакета>
```

### AC-009. Расширение из `src\cfe` опционально

Если каталог `src\cfe` существует, в `Report.txt` должна появиться отдельная корневая секция:

```text
	- Конфигурации.<ИмяРасширения>
```

Если каталог `src\cfe` отсутствует и `extensionRequired=false`, генератор должен успешно сформировать `Report.txt` только по основной конфигурации.

### AC-010. Расширение не объединяется с основной конфигурацией

Не должно быть merged-view.

Объекты основной конфигурации и расширения выводятся в своих корневых секциях.

### AC-011. Результат индексируется MCP

После передачи `Report.txt` в MCP с `INDEX_METADATA=true` поиск должен находить:

```text
Конфигурация
Подсистема
Общий модуль
Документ
Справочник
Регистр сведений
Реквизит
Форма
Макет
Объект расширения, если расширение есть
```

### AC-012. Повторяемость

Два запуска на одной и той же Git-выгрузке дают одинаковый `Report.txt`.

### AC-013. Запуск из Windows Task Scheduler

Генератор должен корректно завершаться с exit code и писать лог в файл при запуске без интерактивной сессии пользователя.

### AC-014. Path portability

Один и тот же код должен работать с путями:

```text
E:\mcp-1c\repos\orders
```

и в будущем:

```text
/opt/mcp-1c/repos/orders
```

без изменения логики генератора.

### AC-015. Порядок объектов стабилен

Объекты внутри корневой секции должны выводиться в порядке ссылок из `Configuration.xml` / `ChildObjects`, как в эталоне. Если ссылки нет, объект выводится после объектов из эталонного порядка и сортируется по полному имени.

### AC-016. Свойства выводятся по правилам whitelist + дополнительные простые свойства

Для поддержанного типа объекта:

```text
1. whitelist-свойства выводятся в фиксированном порядке;
2. дополнительные простые свойства выводятся после whitelist-свойств;
3. сложные неподдержанные свойства не выводятся и фиксируются в diagnostics.
```

### AC-017. Неподдержанные типы используют fallback

Если встречен неподдержанный тип метаданных:

```text
- объект попадает в Report.txt;
- выводятся базовые свойства;
- выводятся безопасные простые XML-свойства;
- unsupportedType фиксируется в diagnostics;
- exit code учитывает warning policy.
```

### AC-018. Формат корневых секций

Формат отступов должен соответствовать эталонному `ОтчетПоКонфигурации.txt`:

```text
	- Конфигурации.<ИмяОсновнойКонфигурации>
		Имя: "<ИмяОсновнойКонфигурации>"
```

Корневая секция начинается с одной табуляции перед `-`.

Если расширение есть, между секцией основной конфигурации и секцией расширения должна быть ровно одна пустая строка.

Если расширения нет, лишняя пустая строка в конце `Report.txt` не добавляется.

### AC-019. CLI MVP

MVP запускается как Python-скрипт:

```text
python generate_config_report.py --config <path-to-config.json>
```

Installable command `generate-config-report` не требуется в MVP.

## 21. Контроль качества

Для проверки качества использовать эталонный файл:

```text
ОтчетПоКонфигурации.txt
```

Проверка не бинарным diff, а по критериям:

```text
1. Совпадает общий стиль.
2. Совпадает иерархия.
3. Совпадают штатные имена свойств.
4. Нет нештатных технических секций.
5. Основные объекты присутствуют.
6. Вложенные объекты присутствуют.
7. Значения свойств выводятся в кавычках.
8. Пустые значения выводятся как "".
9. Списки выводятся блоками.
10. Если расширение есть, оно выводится отдельной корневой секцией.
11. Если расширения нет, отчет по основной конфигурации все равно формируется успешно.
12. Объекты выводятся в эталонном порядке ссылок XML, fallback — по полному имени.
13. Свойства выводятся по whitelist-порядку плюс дополнительные простые свойства.
14. Неподдержанные типы не теряются, а выводятся через fallback.
15. Корневые строки отчета имеют базовый отступ в одну табуляцию, как в эталонном `ОтчетПоКонфигурации.txt`.
```

## 22. Риски

### Риск 1. XML-выгрузка не содержит часть свойств штатного отчета

Решение:

```text
Если свойства нет в XML, генератор его не выдумывает.
Допустимо пропустить свойство.
Запрещено заменять его искусственным техническим полем.
```

### Риск 2. Формат XML отличается для разных типов объектов

Решение:

```text
Делать parser итерационно.
Для неподдержанных объектов выводить базовый блок.
Все пропуски фиксировать в diagnostics.
```

### Риск 3. Расширение сложно представить как штатный отчет

Решение:

```text
Не делать наложение.
Выводить src/cfe отдельной корневой секцией.
Использовать штатные свойства принадлежности.
Если src/cfe отсутствует, пропускать расширение без ошибки при extensionRequired=false.
```

### Риск 4. Windows-специфика попадет в код

Решение:

```text
Вся работа с путями через pathlib.
PowerShell только как внешний runner.
Все настройки через JSON config.
Автотесты путей Windows/Linux.
```

### Риск 5. Дополнительные XML-свойства засорят отчет

Решение:

```text
Выводить только простые скалярные свойства и простые списки.
Сложные структуры фиксировать в diagnostics.
При необходимости добавлять поддержку свойства явно через whitelist.
```

### Риск 6. `warningsAsErrors` будет неоднозначно трактоваться

Решение:

```text
warningsAsErrors фиксируется в config.
--strict является явным CLI override.
Exit codes закреплены в PRD.
```

## 23. Итоговая формулировка задачи

Разработать генератор `generate-config-report`, который по XML-выгрузке основной конфигурации 1С из `src\cf` и, при наличии, одного расширения из `src\cfe` формирует `Report.txt`, структурно и стилистически близкий к штатному отчету Конфигуратора **“Отчет по конфигурации”**.

Расширение является необязательным. Если `src\cfe` отсутствует и `extensionRequired=false`, генератор должен сформировать `Report.txt` только по основной конфигурации и вернуть exit code согласно политике warnings.

Генератор должен выводить дерево метаданных, свойства объектов и вложенные элементы. Он не должен добавлять сведения о физических файлах, BSL-модулях, путях в Git или иных данных, отсутствующих в штатном отчете.

Порядок объектов должен быть детерминированным: корневые секции в фиксированном порядке, объекты внутри секции и вложенные элементы — по порядку ссылок из родительского XML, fallback — по полному имени. Свойства выводятся по whitelist-порядку для типа объекта, дополнительные простые XML-свойства — после whitelist-свойств.

Для неподдержанных типов метаданных используется fallback: базовые свойства, дополнительные простые XML-свойства, diagnostics warning.

Основная среда выполнения MVP — Windows. Код должен быть написан кроссплатформенно, чтобы в дальнейшем без переписывания логики перенести выполнение на Linux.

MVP запускается как Python-скрипт `generate_config_report.py --config ...`; installable CLI entry point `generate-config-report` описан в `pyproject.toml` и использует тот же CLI-слой.

`Report.txt` используется только для `metadatasearch` в MCP. Поиск по BSL-коду остается задачей `codesearch` через `CODE_PATH`.

## 24. Addendum: Source Model Update 2026-05-12

Этот addendum заменяет прежние пункты PRD, где основная конфигурация считалась безусловно обязательной.

Актуальная модель источников:

```text
- generator читает основную конфигурацию из mainConfigPath и/или одно расширение из extensionPath;
- mainConfigRequired управляет обязательностью основного источника;
- extensionRequired управляет обязательностью источника расширения;
- mainConfigPath и extensionPath могут быть отключены пустой строкой;
- хотя бы один путь источника должен быть задан;
- хотя бы один каталог источника должен существовать на момент запуска;
- если доступен только один источник, Report.txt формируется только по нему;
- если доступны оба источника, они выводятся отдельными корневыми секциями;
- если оба источника недоступны, запуск завершается ошибкой с exit code 9.
```
