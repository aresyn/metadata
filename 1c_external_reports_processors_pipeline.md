# Pipeline работы с конфигурациями, расширениями, внешними отчетами и обработками 1С

## 1. Целевая модель

Получается единый продуктовый репозиторий с двумя независимыми контурами:

```text
src/cf, src/cfe  — зеркало хранилища 1С, источник истины = хранилище 1С
src/epf, src/erf — внешние обработки/отчеты, источник истины = GitLab
```

## 2. Итоговая структура репозитория

Пример для продукта `zup`, `upp`, `orders`:

```text
repo/
  src/
    cf/
      ...                    # основная конфигурация, обновляет только gitsync

    cfe/
      ...                    # расширения, обновляет только gitsync

    epf/
      ЗагрузкаГрафиков/
        ЗагрузкаГрафиков.epf
        ЗагрузкаГрафиков.xml
        ...
        manifest.json

      ЗаполнениеПоказателей/
        ЗаполнениеПоказателей.epf
        ЗаполнениеПоказателей.xml
        ...
        manifest.json

    erf/
      АнализНачислений/
        АнализНачислений.erf
        АнализНачислений.xml
        ...
        manifest.json

  tools/
    install-hooks.ps1
    dump-external.ps1
    build-external.ps1
    generate-manifest.ps1
    validate-external.ps1

  .gitlab-ci.yml
  CODEOWNERS
```

Фиксация структуры:

```text
src/epf/<ИмяОбработки>/ — одна внешняя обработка
src/erf/<ИмяОтчета>/    — один внешний отчет
```

Внутри каталога внешней обработки/отчета храним:

```text
.epf / .erf
XML/BSL-выгрузку
manifest.json
```

На MVP бинарники `.epf/.erf` остаются в Git.

# 3. Контур 1: основная конфигурация и расширения

## 3.1. Источник истины

```text
Хранилище 1С
```

## 3.2. Pipeline

```text
Разработчик
  ↓
работает в Конфигураторе
  ↓
помещает изменения в хранилище 1С
  ↓
ежечасный gitsync на 1c-sonarqube
  ↓
обновляет src/cf и src/cfe
  ↓
commit/push в GitLab master
  ↓
SonarQube, если появились новые версии
  ↓
разработчик делает git pull
```

## 3.3. Правила

```text
src/cf  — руками в Git не меняем
src/cfe — руками в Git не меняем
```

Изменения туда попадают только через хранилище 1С и `gitsync`.

# 4. Контур 2: внешние отчеты и обработки

## 4.1. Источник истины

```text
GitLab
```

## 4.2. Pipeline

```text
Разработчик
  ↓
создает feature-ветку external/<JIRA>-<описание>
  ↓
меняет только src/epf/** или src/erf/**
  ↓
precommit4onec / hook синхронизирует binary ↔ XML
  ↓
генерируется manifest.json
  ↓
commit
  ↓
push в feature-ветку
  ↓
Merge Request в master
  ↓
GitLab CI
  ↓
review
  ↓
merge в master
  ↓
deploy-agent загружает .epf/.erf в 1С
```

## 4.3. Что может менять разработчик

Разработчик может менять:

```text
src/epf/**
src/erf/**
```

Разработчик не может менять в external-MR:

```text
src/cf/**
src/cfe/**
tools/**
sync-config.json
.gitlab-ci.yml
```

# 5. Ветки и роли

## 5.1. Ветка `master`

```text
master protected
force push disabled
push в master — только Maintainers
merge в master — только Maintainers
```

## 5.2. Роли

```text
gitsync service token:
  Maintainer
  пушит src/cf и src/cfe в master

DevOps / ответственный:
  Maintainer
  мержит MR

Разработчик external:
  Developer
  пушит feature-ветки
  не пушит в master

Обычный читатель:
  Reporter
```

## 5.3. Кто делает MR

```text
MR создает разработчик.
Merge выполняет ответственный Maintainer после прохождения CI и review.
```

# 6. Manifest

`manifest.json` — генерируемый файл, а не документ, который полностью заполняется руками.

## 6.1. Пример общих полей

```json
{
  "schemaVersion": 1,
  "profile": "bsp",
  "name": "ЗагрузкаГрафиков",
  "kind": "ExternalDataProcessor",
  "product": "ZUP",
  "description": "Загрузка графиков работы сотрудников из Excel.",
  "version": "1.0.0",
  "paths": {
    "root": "src/epf/ЗагрузкаГрафиков",
    "binaryFile": "src/epf/ЗагрузкаГрафиков/ЗагрузкаГрафиков.epf",
    "rootXml": "src/epf/ЗагрузкаГрафиков/ЗагрузкаГрафиков.xml"
  },
  "artifact": {
    "sha256": "",
    "commit": "",
    "pipelineId": "",
    "builtAt": ""
  }
}
```

## 6.2. Откуда берутся поля

```text
kind:
  src/epf → ExternalDataProcessor
  src/erf → ExternalReport

name:
  имя каталога

paths:
  по расположению файлов

description/version/placement:
  для БСП — из СведенияОВнешнейОбработке()
  для УПП — из реквизитов карточки ВнешниеОбработки / УПП-профиля

sha256/commit/pipelineId/builtAt:
  из CI
```

# 7. Профиль БСП

Для конфигураций на БСП: ЗУП, БП, ERP и аналогичные.

## 7.1. Где хранится в 1С

```text
Справочник ДополнительныеОтчетыИОбработки
```

## 7.2. Идентификатор в 1С

```text
Вид + ИмяОбъекта
```

Пример для обработки:

```text
Вид = ДополнительнаяОбработка
ИмяОбъекта = ЗагрузкаГрафиков
```

Пример для отчета:

```text
Вид = ДополнительныйОтчет
ИмяОбъекта = АнализНачислений
```

## 7.3. Metadata

Используем штатную функцию:

```bsl
Функция СведенияОВнешнейОбработке() Экспорт
```

Из нее берем:

```text
Вид
Наименование
Версия
Информация
БезопасныйРежим
Назначение
Команды
```

## 7.4. Deploy для БСП

Deploy-agent:

```text
1. Берет .epf/.erf из GitLab master.
2. Проверяет sha256.
3. Подключается к базе.
4. Ищет элемент ДополнительныеОтчетыИОбработки по Вид + ИмяОбъекта.
5. Если есть — обновляет файл.
6. Если нет — создает.
7. Заполняет Версия, Информация, ИмяФайла, ХранилищеОбработки, Публикация и прочие штатные реквизиты.
```

# 8. Профиль УПП

Для УПП используется отдельный профиль, потому что там внешние обработки хранятся иначе.

## 8.1. Где хранится в 1С

```text
Справочник ВнешниеОбработки
```

## 8.2. Что добавляем в УПП

В справочник `ВнешниеОбработки` добавляем один новый реквизит:

```text
ИмяОбъекта
```

Тип:

```text
Строка, длина 150 или 255
```

## 8.3. Идентификатор в УПП

```text
ВидОбработки + ИмяОбъекта
```

Пример для обработки:

```text
ВидОбработки = Обработка
ИмяОбъекта = ЗагрузкаГрафиков
```

Пример для отчета:

```text
ВидОбработки = Отчет
ИмяОбъекта = АнализНачислений
```

## 8.4. Что используем из существующих реквизитов УПП

```text
ВидОбработки
Комментарий
КомментарийКФайлуИсточнику
ДоступнаАС
ДоступнаФК
ДоступнаАдминам
АдресФайлаВГите
ХранилищеВнешнейОбработки
ТЧ Принадлежность
```

## 8.5. Deploy для УПП

Deploy-agent для УПП:

```text
1. Берет .epf/.erf из GitLab master.
2. Читает manifest.json.
3. Проверяет sha256.
4. Подключается к УПП.
5. Ищет элемент справочника ВнешниеОбработки по ВидОбработки + ИмяОбъекта.
6. Если есть — обновляет ХранилищеВнешнейОбработки.
7. Если нет — создает элемент.
8. Заполняет ВидОбработки, ИмяОбъекта, Комментарий, АдресФайлаВГите.
9. При необходимости заполняет доступность и ТЧ Принадлежность.
```

Без отдельного регистра.

# 9. precommit4onec / локальный hook

Используем для external-контура.

## 9.1. Что делает hook

```text
Если изменился .epf/.erf:
  выгружает его в XML/BSL рядом с бинарником;
  генерирует manifest.json;
  добавляет связанные файлы в commit.

Если изменился XML/BSL:
  собирает .epf/.erf;
  обновляет manifest.json;
  добавляет бинарник и manifest в commit.

Если ошибка выгрузки/сборки:
  commit запрещается.
```

Важно:

```text
Локальный hook — это удобство, не защита.
Его можно обойти через --no-verify.
Поэтому CI обязательно повторяет проверки.
```

# 10. GitLab CI

CI должен быть обязательным для MR в `master`.

## 10.1. Job 1. Проверка путей

CI падает, если разработчик изменил что-то вне:

```text
src/epf/**
src/erf/**
```

Для обычного external-MR запрещены:

```text
src/cf/**
src/cfe/**
tools/**
sync-config.json
.gitlab-ci.yml
```

## 10.2. Job 2. Проверка структуры external

Для каждой обработки:

```text
src/epf/<Name>/
  <Name>.epf
  <Name>.xml
  manifest.json
```

Для каждого отчета:

```text
src/erf/<Name>/
  <Name>.erf
  <Name>.xml
  manifest.json
```

CI проверяет:

```text
каталог соответствует имени файла;
тип соответствует каталогу;
manifest существует;
rootXml существует;
binaryFile существует.
```

## 10.3. Job 3. Генерация/валидация manifest

CI заново генерирует manifest и проверяет:

```text
manifest не расходится с источниками;
description заполнен;
version заполнена;
kind корректен;
profile корректен;
paths корректны.
```

## 10.4. Job 4. Проверка binary ↔ XML

CI должен проверить, что бинарник и XML-выгрузка синхронны.

Минимум для MVP:

```text
если изменился .epf/.erf, XML тоже должен измениться;
если изменился XML, .epf/.erf тоже должен измениться.
```

Лучше:

```text
собрать/выгрузить заново и сравнить результат.
```

## 10.5. Job 5. SHA256

CI считает hash:

```text
sha256(.epf/.erf)
```

И записывает в release/build manifest.

# 11. Deploy-agent

Deploy-agent — отдельный серверный процесс.

## 11.1. Общая логика

```text
1. Берет список измененных/актуальных manifest.json из master.
2. Для каждого manifest берет binaryFile.
3. Считает sha256.
4. Проверяет, что файл соответствует manifest.
5. По profile выбирает стратегию доставки:
   profile=bsp → ДополнительныеОтчетыИОбработки
   profile=upp → ВнешниеОбработки
6. Подключается к базе 1С.
7. Создает или обновляет элемент.
8. Пишет лог установки.
```

## 11.2. Для БСП

```text
ключ поиска = Вид + ИмяОбъекта
хранилище = ДополнительныеОтчетыИОбработки
```

## 11.3. Для УПП

```text
ключ поиска = ВидОбработки + ИмяОбъекта
хранилище = ВнешниеОбработки
```

# 12. Защита 1С от ручной загрузки

Чтобы GitLab действительно был источником истины для `src/epf` и `src/erf`, нужно закрыть ручное обновление в 1С.

## 12.1. Для БСП

Ограничить права на:

```text
ДополнительныеОтчетыИОбработки
```

Обычные пользователи:

```text
могут запускать разрешенные обработки;
не могут добавлять/заменять файлы.
```

Сервисный пользователь deploy-agent:

```text
может добавлять/заменять файлы.
```

## 12.2. Для УПП

Ограничить права на:

```text
ВнешниеОбработки
```

Обычные пользователи:

```text
могут использовать разрешенные обработки;
не могут добавлять/заменять файлы.
```

Сервисный пользователь deploy-agent:

```text
может добавлять/заменять файлы.
```

# 14. MVP-граница

## 14.1. Делаем на MVP

```text
1. Храним .epf/.erf в Git.
2. Храним XML/BSL-выгрузку рядом.
3. Храним manifest.json рядом.
4. Разработчики пушат только feature-ветки.
5. MR создает разработчик.
6. Merge делает Maintainer.
7. CI проверяет только external-зону.
8. Deploy-agent загружает в 1С.
9. Для УПП добавляем только один реквизит ИмяОбъекта.
10. Без отдельного регистра аудита.
```

## 14.2. Не делаем на MVP

```text
1. Не выносим .epf/.erf в GitLab artifacts.
2. Не делаем package registry.
3. Не делаем отдельный реестр аудита.
4. Не делаем server-side pre-receive hook.
5. Не строим сложную модель owner.
```

# 15. Что можно добавить после MVP

```text
1. Вынести .epf/.erf из Git в GitLab artifacts/releases.
2. Добавить отдельный audit-check по SHA256 в 1С.
3. Добавить server-side hook, запрещающий push вне src/epf/src/erf.
4. Добавить автоматический deploy после merge.
5. Добавить package registry для внешних обработок.
6. Добавить отчет по установленным версиям в 1С.
```

# 16. Финальная формула

```text
src/cf, src/cfe:
  Источник истины = хранилище 1С
  Путь доставки = gitsync → GitLab
  Разработчики не пушат

src/epf, src/erf:
  Источник истины = GitLab
  Путь доставки = MR → CI → deploy-agent → 1С
  Разработчики пушат только feature-ветки
  master защищен
```
